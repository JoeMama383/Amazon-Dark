AmazonDark v7.350 — deterministic native splash image seal
===========================================================

DIRECT BASE
-----------
Exact source base: v7.349~cart-shimmer-border-strip-fix.
The accepted Cart 13pt shimmer-border fix, v7.348 native loading-gradient work, and all
other v7.349 production UI behavior are retained.

GOOD/BAD PAIRED CAPTURE
-----------------------
User supplied one explicit transition archive containing two fresh processes in order:
  GOOD: PID 60843, session 1788736127047-60843-transition
  BAD:  PID 60851, session 1788736135955-60851-transition
The user identified the first cold launch as visually correct and the second as the stock-white failure.

SpringBoard launch-artwork path is NOT the differentiator:
  GOOD: snapshot.dark GeneratedDefault at uptime 108435.220410; app session starts 108436.165590.
  BAD:  snapshot.dark GeneratedDefault at uptime 108444.256754; app session starts 108445.070903.
Both launches therefore receive AmazonDark's dark 430x932 GeneratedDefault artwork before the app process presents.

GOOD run:
  - AXUSplashScreenViewController own.before/after occurs at uptime 108438.978 while window=false.
  - No on-window AXUSplashScreenViewController UIImageView is ever emitted by the native-frame recorder.
  - UIApplicationDidBecomeActive occurs at 108439.302.

BAD run:
  - AXUSplashScreenViewController first appears off-window at 108447.690.
  - The same controller is owned again at 108447.772 with window=true.
  - At 108447.997 the native-frame recorder captures:
      controller = AXUSplashScreenViewController
      class      = UIImageView
      rect       = 430x932 (full screen)
      imageSize  = 2400x2400
      contents   = true
      opacity    = 1
    while the controller root UIView itself is already OLED black.
  - UIApplicationDidBecomeActive follows at 108448.009.

ROOT CAUSE
----------
v7.349's ADOwnAmazonSplash7307() owns only vc.view.backgroundColor on a cold launch while
intentionally preserving Amazon's native splash contents. That is insufficient when Amazon mounts
an opaque full-screen UIImageView above the controller floor. The bad capture proves that this child
image plane reaches the window only on the failing launch; the good launch never exposes it. This
explains both the intermittency and why repeated black-floor fixes could not guarantee zero white.

The inherited v7.337 launch audit explicitly left "a bright child inside Amazon's native splash" as
an unresolved possibility. The paired v7.349 capture now proves that exact case on-device.

V7.350 PRODUCTION FIX
---------------------
For AXUSplashScreenViewController and TezBaseSplashScreenViewController only, the existing cold/
scene-reconstruction ownership path now installs an app-side splash seal before window presentation:
  - full controller-bounds UIView
  - OLED-black background
  - noninteractive / accessibility-hidden
  - autoresizes with the controller
  - zPosition FLT_MAX and bringSubviewToFront on every ownership/layout pass
  - existing AmazonDark splash-logo.png centered at 62% of controller width
  - named layers AmazonDarkSplashSeal7350 and AmazonDarkSplashSealLogo7350 for the retained probe

The seal is created from viewDidLoad/appearance ownership after Amazon builds the controller but before
the bad-run image plane can become a visible window frame. Amazon continues to own the controller's
presentation lifetime and dismissal. There is no custom duration or release event.

WARM / SWITCHER PRESERVATION
----------------------------
The retained v7.307 ordinary-warm contract is unchanged. On a genuine same-scene warm resume,
ADOwnAmazonSplash7307() still hides the exact replayed splash controller; v7.350 hides the seal with
that controller. No warm loading transition is fabricated and no app-switcher view is introduced.

WHY V7.330 SCENE OVERLAY IS NOT RESTORED
----------------------------------------
Historical v7.330/v7.335/v7.336 process-scoped scene overlays could cover arbitrary cold-launch pixels,
but later probes documented false-cold classification, replacement-scene continuity problems and
20-second hard-cap failures. The v7.349 paired capture gives a narrower proven owner inside Amazon,
so v7.350 fixes that owner without reintroducing the old SpringBoard launch state machine.

RUNTIME / PERFORMANCE CONTRACT
------------------------------
New production recurring work: none.
No MutationObserver, setInterval, requestAnimationFrame loop, web-scroll listener, polling loop,
Home-readiness scheduler, scene overlay, PID classifier, hard cap, or delayed release is added.
The only new image load is one dispatch_once app-side load of the already-shipped splash-logo.png,
first reached from the native splash controller after UIKit is initialized.
